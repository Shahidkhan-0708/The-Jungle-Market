# Design: Jungle Market Connected Story UI

Generated by gstack Office Hours on 2026-09-13  
Branch: main  
Status: DRAFT  
Mode: Builder

## Problem Statement

Jungle Market has three substantial portals, Buyer, Artisan, and Ambassador, but its portfolio value depends on making them feel like one intentional product. The redesign must give all three roles equal visual quality while making their relationship understandable within seconds.

## What Makes This Cool

One real product becomes the narrative spine. The portfolio demo follows it from an artisan's draft, through an ambassador's field verification, to a buyer's discovery and purchase. Each portal remains useful by itself, but together they tell one traceable human story.

## Constraints

- Preserve the Expo/React Native architecture and web compatibility.
- Build on the existing `THEME` tokens and the Earthy Artisan Sanctuary direction.
- Improve Buyer, Artisan, and Ambassador rather than polishing only one role.
- Keep the interface accessible, responsive, keyboard-usable on web, and usable with reduced motion.
- Treat `skiper40.jsx` as a reference. It depends on Next.js links and web CSS pseudo-elements, so it cannot be imported directly into React Native screens.
- Preserve unrelated work already present in the working tree.

## Premises

1. All roles share foundations, while information density and task emphasis vary by role.
2. One connected product journey is the clearest portfolio narrative.
3. Skiper40 contributes selective interaction patterns, not the visual system.
4. Recruiter-facing polish includes interaction states, accessibility, responsiveness, and an explanation of design decisions.

## Landscape Findings

- Current ecommerce examples reward distinctive art direction when navigation and product information stay clear.
- Multi-sided marketplace case studies are easiest to understand when the shared system and cross-role workflow are visible.
- Recruiters need to identify the problem, decisions, and implementation quality quickly; attractive screens alone are insufficient.

## Approaches Considered

### A: System-first redesign

Consolidate all tokens and primitives before redesigning screens. Safest long-term structure, but the portfolio-defining experience appears late.

### B: Surface-polish sprint

Polish visible screens and interactions immediately. Fastest screenshots, but leaves inconsistent states and weak system evidence.

### C: Story spine plus design system

Build the connected product journey first, derive the shared system from real needs, then expand it across every screen. Selected because it combines a memorable demo with credible UI engineering.

## Recommended Approach

### Phase 1: Audit and baseline

1. **Improve UI** audits every screen for hierarchy, spacing, consistency, responsive behavior, and interaction problems.
2. **Better Accessibility** checks contrast, focus order, labels, touch targets, reduced motion, screen-reader semantics, and keyboard behavior.
3. **Browser Control and QA** capture baseline screenshots and verify the Buyer, Artisan, and Ambassador happy paths.
4. Create a screen inventory with states: default, loading, empty, offline, error, partial, disabled, and success.

Deliverable: prioritized UI issue ledger with before screenshots and acceptance criteria.

### Phase 2: Lock the editorial nature system

1. **UI UX Pro Max** selects the editorial marketplace pattern, responsive layout rules, typography pairing, color usage, data-density guidance, and interaction conventions.
2. **Design System** normalizes semantic tokens in `src/theme/theme.js`: canvas, surface, text, action, status, border, shadow, radius, spacing, type scale, and motion.
3. **Better Colors** validates contrast and assigns colors by meaning rather than by screen.
4. **Better Typography** defines display, heading, body, label, caption, numeric, and long-form story styles with predictable line heights.
5. **Better Layout** defines page shells, grids, safe areas, content widths, spacing rhythm, and mobile/web breakpoints.

Deliverable: a compact token specification and reusable component contract shared by all roles.

### Phase 3: Build the product-journey spine

Use one featured basket as the canonical demo object:

1. Artisan creates the listing, adds materials, region, price, photos, and an audio story.
2. Ambassador reviews identity, origin, material evidence, and fair-price notes.
3. Buyer discovers the verified item, reads or listens to its story, and completes the purchase.
4. Preserve the selected product and journey status while switching roles.

**Prototype** tests the journey with realistic content before broad screen work. **UI Styling** then establishes the photographic composition, editorial hierarchy, organic surfaces, and restrained decorative details. **Animation Vocabulary** names the intended transitions before implementation so motion communicates continuity instead of adding spectacle.

Deliverable: one end-to-end, portfolio-ready flow connecting all three portals.

### Phase 4: Use Skiper40 selectively

Adapt, do not directly import, these ideas from `src/components/ui/skiper-ui/skiper40.jsx`:

- Animated underline for editorial text links.
- Small directional-arrow reveal for “Meet the artisan,” “View verification,” and “Follow the journey.”
- Origin-aware hover animation on web.
- Equivalent press feedback and icon motion on native.

Implement these through a cross-platform `EditorialLink` primitive using React Native `Pressable` and `Animated`, with web hover behavior guarded by `Platform.OS`. Respect reduced-motion settings and retain the attribution required by Skiper UI's free license.

Do not use Skiper40 for primary purchase buttons, destructive actions, dense navigation, or every link. Its job is to make story transitions feel crafted.

### Phase 5: Expand across every role

Apply the system to all remaining screens in coherent batches:

1. **Artisan:** dashboard, selling workflow, orders, earnings, and guild.
2. **Ambassador:** queue/dashboard, verification, network, and reports.
3. **Buyer:** home, categories, product detail, checkout, success, orders, bulk buying, and profile.

For each batch, **Better Interface** checks the combined layout, type, color, accessibility, writing, and interaction quality. **Better Writing** shortens labels, clarifies empty/error states, and keeps the three role voices consistent. Shared primitives replace repeated local styles only when at least two real screens need them.

Deliverable: equal design quality and complete states across every portal.

### Phase 6: Motion and interaction polish

1. **Find Animation Opportunities** identifies transitions that explain state or preserve context.
2. **Improve Animations** implements role switching, journey progress, verification success, cart feedback, audio playback, and content entrances.
3. **Review Animations** removes distracting motion and checks duration, easing, interruption, performance, and reduced-motion behavior.
4. Skiper-derived link motion remains a small accent within the broader motion language.

Deliverable: a documented motion map with purposeful transitions and fallbacks.

### Phase 7: Design and implementation QA

1. **Design Review** inspects screenshots at representative phone, tablet, and desktop widths.
2. **QA** exercises complete flows, role switching, long text, zero results, network failure, sold-out products, rejected verification, cart changes, and payment failure.
3. **Better Accessibility** runs a final pass after visual corrections.
4. Browser automation records the final recruiter walkthrough and compares it with the baseline.

Deliverable: verified flows, an issue-free critical path, and final screenshots/video.

### Phase 8: Package the portfolio story

Create a short case study with:

1. The original fragmentation problem.
2. The connected-product insight.
3. The token and component decisions.
4. Before/after evidence from all three roles.
5. Accessibility and edge-state examples.
6. A 60–90 second guided demo: Artisan → Ambassador → Buyer.

**Figma** is optional for presenting foundations, components, and annotated flows; it should document the implemented system, not become a parallel source of truth. **Image Generation** may create missing editorial environment imagery only when existing licensed assets are insufficient, with consistent direction and documented usage.

## Success Criteria

- A first-time viewer can explain the three-role relationship within 30 seconds.
- The full featured-product journey works from artisan draft through buyer purchase.
- Every existing screen uses the shared semantic tokens and role-aware primitives.
- Critical controls meet a minimum 44px touch target.
- Text and essential UI meet WCAG AA contrast targets.
- Keyboard navigation works on web, focus is visible, and controls have accessible names.
- Reduced-motion users receive equivalent feedback without decorative movement.
- Phone, tablet, and desktop layouts have no clipped content or accidental horizontal scrolling.
- Loading, empty, offline, error, partial, and success states exist for critical workflows.
- Automated smoke tests and the three manual role walkthroughs pass.
- The portfolio case study includes before/after evidence, design reasoning, and a short recorded demo.

## Distribution Plan

The existing Expo web/mobile delivery remains the distribution path. Add a stable portfolio demo build and a direct route or guided entry point for the three-role product journey. CI should run smoke tests and the web QA script before deployment; deployment automation can be finalized during engineering review.
